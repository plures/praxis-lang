# RFC-0007 — Schema-Bound Procedure Contracts

## Status

Proposed implementation slice: `px-check` and `px_compiler::parse_checked`.

## Problem

The language schema currently proves that a `.px` file has valid syntax and
AST shape. It does not prove that the runtime named by that file provides the
actions it calls, accepts the arguments it supplies, or can lower every value
reference it contains. The result is a valid parse followed by a runtime
failure, often after state has already changed.

## Decision

Every procedure file entering a checked build MUST pin the generated contract
surface it was authored against:

```px
# px-schema: plures.agens.spine@1#<generated-fingerprint>
```

The pinned schema is a generated, versioned description of:

- callable names;
- required and optional named parameters with Praxis types;
- result types;
- record/entity field shapes;
- runtime lowering capabilities;
- effects and capability requirements once RFC-0003 is materialized.

The language-level schema remains the grammar/AST schema generated by
`px-schema`. A procedure schema is its companion: it binds one source file to
one executable host surface. Neither replaces the other.

## Compile-Time Gate

`px_compiler::parse_checked(source, catalog, profile)` performs these gates in
order:

1. Reject `[parser-skip]`; a comment is never executable configuration.
2. Require and parse the source-local `px-schema` pin.
3. Require the host catalog to carry the identical schema ID, version, and
   fingerprint.
4. Parse to the canonical AST.
5. Fail closed for every call absent from the catalog.
6. Fail for missing, unknown, or statically incompatible named arguments.
7. Fail for an AST reference form that the selected runtime profile cannot
   lower, including accessor values in call parameters when unsupported.

The compiler emits stable diagnostics (`PX1000` through `PX1011`) so editors,
CI, and the Decision Ledger can link a failure to the precise contract breach.

## Schema Generation and Runtime Handshake

The host owns implementation but not the contract format:

1. A host declares typed callable contracts, preferably from typed `.px`
   `function` declarations plus generated bindings for Rust handlers.
2. A deterministic generator emits the catalog and its fingerprint.
3. CI checks every changed `.px` with that catalog and rejects a stale pin.
4. At startup, the runtime recomputes its catalog fingerprint from registered
   handlers and refuses to load a procedure whose pin differs.

This prevents the two drift directions that caused the autonomous-dispatch
failure: a procedure calling an action that was never registered, and a
runtime accepting source whose value-reference lowering it cannot perform.

## Decision Ledger Evidence

Each checked build records a durable evidence record containing the procedure
content hash, schema ID/version/fingerprint, target runtime profile, checker
version, diagnostics, and result. A release or deployment gate accepts only a
successful record whose source and contract fingerprints still match the
artifact being deployed.

## Rollout

1. Land `px-check` and checked compilation in `praxis-lang`.
2. Generate one schema catalog for the Spine runtime and add pins to its
   procedures.
3. Make the existing parser-only path test-only; production loaders call
   `parse_checked` and verify the runtime handshake.
4. Require the checked compilation and ledger evidence in CI before merging a
   changed `.px` file.
5. Extend the catalog with RFC-0003 effects/capabilities and use the same
   fingerprint for authorization as well as type/lowering validation.

## Non-Goals

- Inferring a host contract from arbitrary runtime code at load time.
- Permitting unknown actions for forward compatibility.
- Treating a commented declaration as a schema, configuration, or contract.
- Replacing behavioral constraints or Decision Ledger review with type checks.
